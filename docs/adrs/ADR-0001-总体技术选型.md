# ADR-0001: SignalFlow 总体技术选型与框架分层

状态：accepted（依据用户明确要求与已确认设计文档）

## 背景

什么真实需求、约束或冲突要求此决策？SignalFlow 需要搭建可长期演进的工程骨架：客户反馈决策工具的核心闭环（收集 → 去重聚类 → 痛点归纳 → 影响评估 → 优先级 → 决策 → 任务 → 回复回传）依赖 AI 编排与多模型接入；同时要求可容器化部署、可私有化（政务版）、可 CI/CD。用户明确指定基于 Python 实现，并要求引入 LangGraph、LiteLLM、Docker 部署与 GitHub CI/CD。

## 考虑的方案

| 方案 | 对本需求的适配度 | 成本或风险 | 证据 |
| --- | --- | --- | --- |
| Python + FastAPI（后端） | 高：异步高性能、Pydantic 校验、生态成熟，适配 AI 工作流 | 同步场景略重；需团队熟悉 | 官方文档；社区广泛采用 |
| LangGraph（AI 工作流编排） | 高：有状态图编排明确支持"多步 AI 管道 + 人工决策点 + 回退/重试" | 需要学习图状态模型；版本迭代较快 | 用户明确要求；官方文档 |
| LiteLLM（多模型网关） | 高：统一 OpenAI/Claude/本地 Ollama 等接入、密钥集中、降级切换 | 需维护网关配置；成本受调用频率约束 | 用户明确要求；官方文档 |
| Vue 3 + TypeScript（前端，默认候选） | 中高：组件化、响应式、生态完善，适配管理后台看板 | 未最终锁定，政务系统有大量 Vue 存量 | 常见前端选型；待用户确认 |
| PostgreSQL + pgvector（数据+向量） | 高：关系数据与向量检索一体，支持私有化 | 需运维 PostgreSQL；大数据量需调优 | 官方文档；VoC 类项目常见组合 |
| Docker Compose（开发/交付部署） | 高：一体化编排后端/前端/数据库/向量库，私有化友好 | 生产高可用需额外编排（K8s） | 用户明确要求 |
| GitHub Actions（CI/CD） | 高：与 GitHub 仓库集成，构建/测试/镜像一条龙 | CI 运行时长与配额；自托管需要配置 | 用户明确要求 |

未强制引入的替代：单体 Node 全栈、无容器裸机部署——在私有化、可维护性、多服务编排上不符合本需求，不予采用。

## 决策

- 总体架构：前后端分离——`backend/`（Python）+ `frontend/`（Web）+ `deploy/`（Docker 编排）+ `.github/workflows/`（CI/CD）。
- 后端：FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic；AI 工作流用 LangGraph（图状态编排）；LLM 统一接入用 LiteLLM；持久化默认 PostgreSQL + pgvector。
- 前端（默认候选，待确认）：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Axios。
- 部署：Docker Compose 编排 backend/frontend/postgres(+pgvector)；提供 Dockerfile、.dockerignore、环境变量示例。
- CI/CD：GitHub Actions 提供 lint、测试、前端构建、镜像构建的 CI 与部署 CD 骨架。

## 后果与所有权

- 收益：分层清晰、边界可测；AI 工作流可演进（新模型/新步骤只改图节点）；多模型可降级；容器化支持政务私有化部署。
- 成本或新风险：LangGraph/LiteLLM 的版本演进需要跟进；LiteLLM 网关配置需要维护；前端选型未最终确认；LLM 成本受 token 预算约束。
- 项目自身仍需拥有：业务服务层逻辑（影响评估、优先级算法）、渠道适配器、权限与审计、政务分级/督办规则；这些不因引入框架而外包。
- 迁移、回滚或退出条件：若 LangGraph 不适合，AI 编排可收敛为普通 service 顺序调用；若 LiteLLM 不满足，可退回按 provider 封装；Docker Compose 可平滑扩展到 K8s。

## 置信度与重访触发

- 置信度：高——后端、AI、部署、CI 四项按用户要求确定；前端为默认候选，置信度中。
- 重访时机：当前端选型被用户确认或否决时；LangGraph/LiteLLM 出现不兼容升级或无法满足政务私有化要求时；政务版合规需求要求更换数据存储时。
