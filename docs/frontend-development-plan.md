> 关联文档：`docs/project-spec.md`（稳定产品规格）、`docs/current-state.md`（当前状态）、`docs/next-stage-plan.md`（下一阶段计划）、`docs/adrs/`（架构决策记录）。

## 1. 本阶段目标与边界

### 1.1 目标

- 用**模拟数据**把前端从入口开始打通，按业务需求与功能切片逐步推进，达到"从入口进入 → 看到反馈信号 → 形成洞察 → 支撑决策 → 追踪行动"的全流程可演示闭环。
- 前端设计**紧凑、信息密度合理**，不做大段文字或复杂展板，突出"客户反馈决策工具"的产品理念。
- 所有计划、需求、设计规范与技术参考**以 Markdown 落盘到项目内**（不是 Word），供后续切片持续遵守。

### 1.2 边界（本阶段不做）

- 不接后端真实数据；后端契约仅作为前端类型对齐的依据（`frontend/src/types` 与 `backend/app/schemas` 保持同步）。
- 不接入真实渠道、LLM、登录鉴权（统一身份认证留接口位，不做实现）。
- 不引入大型组件库（Ant Design 等）——本阶段以轻量自研组件 + CSS 变量主题为主，避免重依赖；后续若确需组件库再按 ADR 决策。

### 1.3 前置条件

- 工程骨架已验证：前端 `npm run build` 通过（vue-tsc + vite），`docker compose config` 通过。
- 后端契约已定义：`POST /api/v1/feedbacks`、`GET /api/v1/feedbacks/{id}`、`GET /api/v1/insights`。

## 2. 产品理念与前端设计理念

SignalFlow = **从反馈噪音里识别决策信号，让客户声音可流动、可解释、可行动**。

前端页面围绕这条理念组织，每条设计规则都对应该理念的一环：

| 产品理念 | 前端设计原则 | 落地表现 |
| --- | --- | --- |
| 反馈是信号不是噪音 | **信号优先** | 每条反馈都可一眼看到来源、要点、归属主题，无冗余填充 |
| 噪音要变成洞察 | **可解释** | 每个主题/痛点都带"证据链"，可下钻到原始反馈原文 |
| 洞察要支撑决策 | **决策焦点** | 每屏只突出一个核心决策点（如优先级/督办等级），其余为支撑信息 |
| 决策后要行动闭环 | **动作可达** | 页面上的状态/操作可直接跳转到下一步行动，不打断链路 |
| 政务场景可落地 | **克制稳重** | 高对比、低装饰、数据不出域、资源本地化 |

三条铁律（贯穿所有页面）：

1. **一屏一焦点**：每个页面聚焦一个用户任务，主区域占绝对视觉权重。
2. **可扫读**：字段文字 ≤ 4 字、按钮 ≤ 4 字、数值优先；用户 3 秒内能找到主要信息。
3. **紧凑不堆砌**：以 4px 基准间距控制密度（见 §6.2），宁可少放一块卡片，不放半块废卡片。

## 4. 前后端衔接流程（mock 先行，无痛切换）

### 4.1 数据流层次

```
页面组件（views）
   │  组合式 API / 局部状态
   ▼
Pinia Stores（业务状态唯一入口）
   │  调用 api 适配层
   ▼
api 适配层（src/api/*.ts）──按环境切换──▶ mock 数据源（src/mocks/*）[本阶段]
   │                                      └─▶ 真实 HTTP 后端（后续阶段）
   ▼
类型契约（src/types/index.ts）与后端 app/schemas 对齐
```

### 4.2 Mock 切换机制

- **约定**：api 层函数签名与真实后端接口一一对应（`fetchFeedbackList` / `fetchInsightDashboard` 等）；内部通过 `import.meta.env.VITE_USE_MOCK !== 'false'` 决定返回 mock 还是发起 HTTP 请求。
- **默认**：`VITE_USE_MOCK` 未设置即走 mock（本阶段默认 mock），后续接后端时在 `.env` 设 `VITE_USE_MOCK=false` 即可，**页面与 store 代码零改动**。
- **类型契约**：mock 数据必须通过 `src/types` 类型校验（`satisfies` / 显式类型标注），防止 mock 与后端契约漂移。

### 4.3 契约演进规则

- 后端 schema 变更（如新增字段）→ 同步更新 `src/types/index.ts` → mock 数据补齐 → 页面按需消费。
- 后端接口尚未实现的字段，前端类型中预留 `skeleton?: boolean` 或可选字段，不允许用 `any` 绕过。

## 5. 设计规范（色调 / 密度 / 布局）—— 前端实现必须遵守

以下规范由开源设计体系调研转化而来（来源见 §7），是本阶段及后续所有前端的实现标准。

### 5.1 色调体系（设计 Token，CSS 变量）

**基调选择（2026-10-14 调整版）**：综合"政务/公共服务"（高对比海军蓝）、"金融 Dashboard"（深底+绿色正指标）、"SaaS 信任蓝"（#2563EB）三类参考，初版采用**稳重海军蓝为主、品牌蓝为行动色**的语义色板；经用户演示反馈（"整体配色偏深，需要淡色有活力"）后调整为：**浅色主题下侧栏由深海军蓝改为白/淡底 + 品牌蓝活跃项，页面背景淡蓝灰，保留品牌蓝为行动色、绿色仅用于正向信号**的"淡色有活力"风格。避免紫色渐变、霓虹色等"AI 通感"配色。

| Token | 值（浅色） | 用途 | 参考来源 |
| --- | --- | --- | --- |
| `--sf-primary` | `#2563EB` | 主行动色：按钮、链接、选中态、侧栏活跃项 | SaaS 信任蓝（ui-ux-pro-max colors#1） |
| `--sf-primary-strong` | `#1E293B` | 强调文字/标题深色（不再作侧栏底色） | 浅色 SaaS 深灰阶 |
| `--sf-sidebar-bg` | `#FFFFFF` | 侧边栏底（浅色主题淡色，活跃项品牌蓝） | 用户反馈淡色化 |
| `--sf-sidebar-text` | `#1E293B` | 侧栏主文字 | 同上 |
| `--sf-sidebar-muted` | `#64748B` | 侧栏次要图标/标签 | 同上 |
| `--sf-sidebar-border` | `#E8EDF4` | 侧栏右分隔线 | 同上 |
| `--sf-bg` | `#F4F7FB` | 页面浅色背景（淡蓝灰） | 淡色有活力用户反馈 |
| `--sf-surface` | `#FFFFFF` | 卡片/内容表面 | 同上 |
| `--sf-border` | `#E2E8F0` | 边框、分隔线 | colors#1 |
| `--sf-text` | `#0F172A` | 主文本 | colors#14 |
| `--sf-text-secondary` | `#475569` | 次要文本、说明 | 常规阶梯 |
| `--sf-success` | `#22C55E` | 正向信号：已解决、已回传、督办正常 | Financial Dashboard 绿色指标（colors#7） |
| `--sf-warning` | `#F59E0B` | 预警：高优先级、待处理超时 | Analytics 琥珀高亮（colors#8） |
| `--sf-danger` | `#EF4444` | 危险：敏感舆情、督办超限 | 常规危险色 |
| `--sf-info` | `#0EA5E9` | 中性信息：主题标签、图标辅助 | Service 天蓝（colors#5） |

- 明暗主题：浅色为默认（政务办公场景主用），深色为主题切换项；实现仿 vue-vben-admin 的 CSS 变量双套（`:root` / `.dark`）+ `html.dark` 类名切换；深色主题侧栏保留深色面板（`--sf-sidebar-bg: #0B1120`）。
- 所有颜色只允许通过 token 引用，禁止页面组件内硬编码色值。
- 全屏排版：`body line-height: 1.6`（统一行距），内容区 `max-width: 1480px; margin: 0 auto`（1920 全屏下避免行过长/信息密度稀释），顶栏 56px；页面栅格在 1200/1100/1000/700/640px 断点折叠，兼顾侧边栏窄窗与完整屏幕。

### 5.2 信息密度与紧凑标准

以 Ant Design compactAlgorithm 与 ProTable 密度实践为蓝本，结合"一屏一焦点"原则：

| 维度 | 标准 | 说明 |
| --- | --- | --- |
| 间距基准 | 4px；卡片 padding **12–16px**；卡片间距 **12px**；页面内容区 padding **16–20px** | 比常规后台更紧凑（常规多为 24px） |
| 表格 | 行高 **40px**（紧凑密度）、列数 ≤ 8、表头 12px 字号、正文 13px | 一屏至少 10 行可见 |
| 字号层级 | 24（页面大数字）→ 16（页面标题）→ 14（卡片标题/正文）→ 13（表格/次要）→ 12（辅助说明） | 层级最多 5 级，不滥用 |
| 指标卡 | 每张卡：1 个主数字（20–24px）+ 至多 2 行辅助（环比/说明），总高 ≤ 92px | 指标行一屏放 4–6 个 |
| 文案 | 字段 Label ≤ 4 字；按钮 ≤ 4 字；页面内不出现段落式说明（如需提示放 tooltip） | 借鉴 Ant Design Pro 命名规范 |
| 内容上限 | 单页主工作区组件数 ≤ 6 块；超过则分片子页 | 防止"复杂展板" |

### 5.3 布局规范

- **整体**：左侧固定侧边栏（宽 64–72px 图标式 + 折叠态，或 200px 文字态），顶部 48–56px 顶栏（页面标题 / 用户区 / 主题切换），内容区自适应。
- **栅格**：内容区 12 栏弹性网格，卡片跨栏 4/6/8/12，间距 12px。
- **总览页（FS-1）**：上=指标行（4–6 个 KPI 卡）→ 中=信号趋势图（时间序列）→ 下=双栏（待处理反馈列表 + 优先级信号榜）；总高度控制在一屏半以内。
- **反馈列表（FS-2）**：顶=筛选条件单行（渠道/状态/关键词）；主体=紧凑表格；详情=右侧 480px 抽屉（原文+归属+操作）。
- **洞察页（FS-3）**：左=主题/痛点列表（紧凑卡，显示反馈数与强度条）；右=主题详情区（证据链列表 + 评分卡）。
- **空白/加载/错误态**：所有数据区必须有 skeleton 加载态与空态文案（参考 ui-ux-pro-max ux-guidelines）。

### 5.4 视觉基调与品牌元素（参考 frontend-design skill）

- **设计方向**：`Industrial / Editorial`（工业克制 + 编辑式排版）——避免通用 AI 美感（不堆叠紫色渐变、不使用 Space Grotesk 等"AI 默认字体"）。
- **品牌隐喻**：以"信号波形/流动线条"作为品牌图形元素（Logo、趋势图装饰、加载动画），呼应 SignalFlow 之名。
- **字体**：正文用系统字体栈 `-apple-system, "Segoe UI", "Microsoft YaHei", sans-serif`；数字/指标用 `font-variant-numeric: tabular-nums` 保证对齐。**不引入外部 webfont**（政务内网可能无外网，资源必须本地化）。
- **动效**：仅关键交互使用 150–250ms 过渡（hover、抽屉滑入、状态徽标变化）；页面加载允许一次信号线绘制动画；遵守 `prefers-reduced-motion`。
- **图标**：内联 SVG 图标集（本地化，不引 CDN；后续如需图标系统按 ADR 决策）。
- **背景质感**：浅色背景可用极淡的网格/等高线纹理（`linear-gradient` 实现，成本低不引图），深色面板可用微噪点，避免纯白死板。

### 5.5 政务适配的额外约束

- 默认高对比度模式：正文对比度 ≥ WCAG AA（4.5:1），token 色板已满足。
- 数据不出域：无外部字体/图标/CDN/统计脚本依赖，构建产物全部本地资源。
- 看板与关键页面支持"导出报告"入口（本阶段为 UI 占位，后续接导出服务）。

## 7. 验证策略（本阶段）

- **每切片**：`npm run type-check` 无错 → 浏览器（Docker/本地 dev）可见该切片交互生效 → 对照 §3.3 验收表。
- **全流程**：`npm run build` 通过 → `docker compose up` 后 `http://localhost` 可访问 → 按 FS-0→FS-5 顺序人工走查一遍闭环（进入 → 看信号 → 下钻反馈 → 看洞察 → 建任务 → 回传）。
- **设计符合度**：按 §5 清单抽查（间距/字号/色板引用/文案长度/组件数），不使用模型评审代替人工走查证据。
